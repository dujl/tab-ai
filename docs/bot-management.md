# BOT、多账号与群聊管理

## 接入多个 BOT

同一实例可在向导中重复执行接入，支持多个同平台 BOT 或跨平台组合。每个连接有独立 `id`、凭证引用、`allowedUsers`、角色和可选 `defaultWorkspace`。消息路由必须包含 BOT ID，不能只根据平台名称定位会话。

查看：`tab-ai bots`、Dashboard“机器人”、聊天 `/tab bots`。聊天中的列表和管理中心仅在 Manager BOT 单聊向已授权用户提供；群聊和普通 BOT 不展示这些入口。

## Manager 与 scoped

| 角色    | 聊天管理范围                                               | 不代表什么                     |
| ------- | ---------------------------------------------------------- | ------------------------------ |
| Manager | 已授权用户在 BOT 单聊中可查看/管理全局会话，修改 BOT 角色  | 不自动把所有群成员加入授权用户 |
| scoped  | 自身范围，按 BOT、用户、聊天隔离；可创建自己的子会话与任务 | 不提供操作系统文件沙箱         |

在接入时选择角色，或由 Manager 的已授权用户在与该 BOT 的单聊中发送：

```text
/tab bot-role <BOT_ID> manager
/tab bot-role <BOT_ID> scoped
```

本机可用 `tab-ai bot-role <BOT_ID> manager|scoped`；Dashboard 下拉框使用相同持久化操作。角色变化立即影响后续管理检查，不能据此承诺撤销原生进程已经读取到的内容。

Manager 的全局能力具体包括 `/tab bots`、会话列表/统计、`/tab manage <ID> status|history|tools|close|open|stop` 和角色修改。任务专用命令仍按当前聊天/用户选取；原生审批仍检查原请求发起人。会话管理中心、列表/数量查询、跨会话操作和 BOT 角色管理均只在 Manager BOT 单聊启用；直接命令和旧卡片回调也逐次检查。群聊和普通 BOT 保留 `/tab menu`、`/tab status` 等当前会话设置、新话题、任务树与群模式操作，不提供全局管理导航。详见[功能与权限边界](capabilities.md)。

## 会话与记忆隔离

聊天路由基于平台、BOT、聊天、话题/虚拟线程和发送者。不同账号的工作 session 不自动合并。原生会话 ID 分别保存；主聊天与独立话题也分开。

这不意味着机器上的所有资源都隔离：同 workspace 的文件、同系统用户下原生 Agent 的全局配置/记忆机制可能共享。tab-ai 不把全机 HOME 自动拆成独立用户环境。新子任务默认继承直接父级目录，修改本节点不会追改其他节点。

## 显示名称与默认目录

Dashboard 可改本机 BOT 显示名及新会话默认目录。显示名不修改平台应用名称；目录不迁移已有 session。新建子会话未指定目录时，优先继承当前直接父会话的目录；父级不可用时才回退同 Bot、聊天、用户的主会话目录，再使用 Bot/实例默认目录。明确指定的目录优先；主会话后续切目录不迁移已有子会话。

新建机器人默认名称为 `tab-ai-botN`，序号考虑已保存的旧机器人和向导预留，避免取消后重复占用。平台上已经创建的机器人名称不会被自动改写。

## 飞书群模式

| 模式              | 非 @ 消息        | @ 消息       | 参考上下文                   |
| ----------------- | ---------------- | ------------ | ---------------------------- |
| `mention`（默认） | 不收集、不触发   | 授权用户触发 | 不自动附加群历史             |
| `context`         | 收集参考，不回复 | 授权用户触发 | 可给普通工作轮提供已收集参考 |
| `auto`            | 授权用户可触发   | 授权用户触发 | 可使用已收集参考             |

在群内按当前触发方式发送 `/tab group-mode context`，也可由本机执行：

```bash
tab-ai group-mode <BOT_ID> <oc_群ID> context
```

Dashboard“机器人 → 群行为模式”可以按群设置。全量模式需要平台授予 `im:message.group_msg` 等实际接收权限；本地切换不能代替平台授权与应用发布。

设置或查询 context/auto 时，框架用当前 BOT 在目标群读取一条消息检查有效权限，消息内容不进入 Agent。缺失时飞书卡片展示当前应用的权限申请按钮和“重新检查权限”，工作台弹出链接与二维码，终端提供同一入口。网络或群成员状态异常时明确显示“尚未确认”。申请、发布及管理员审核完成后重新检查即可，无需再次保存模式。飞书二维码图片上传不可用时，卡片保留可点击的申请链接。

新建飞书 BOT 的扫码授权默认申请 `im:message.group_msg`；已有应用凭证接入也展示当前应用的权限入口及二维码。申请权限不会打开自动群回复，群模式仍默认 mention。

自然语言管理请求通过独立意图识别提取参数，再调用管理 API。`/tab` 命令直接由框架处理，不经过工作 Agent。用户说得不明确时应澄清，不猜测跨群/全局修改。

任务树不自动继承群历史；群聊只提供创建和交流的入口。上下文模式不表示有能力读取 BOT 加群前或平台未投递的全部消息。

## 其他平台

飞书有原生话题。微信采用私聊、引用映射和 `/tab to`；企微、钉钉采用其已实现的群/私聊接收能力与虚拟子会话。不要把飞书的三种全量模式推断为所有平台都支持。每个平台接入方式与限制见[首次接入](onboarding.md)、[微信与企微](wechat-wecom.md)。

当前 Dashboard 不提供授权用户列表编辑、远程删除平台 BOT 或连接开关。修改授权用户等底层配置前，应检查运行任务并按[运维步骤](operations.md)重启。

## 群主会话总控与独立话题

飞书群中的普通主会话默认统筹当前用户新建的独立话题，话题交付摘要回传主会话，无需开关。唯一的输入响应模式设置是 `group-mode`；不会把不同 BOT、群或成员的上下文合并。若首条输入在新话题，框架会自动建立对应的主会话关联。

- 新建的普通话题使用独立 session 与原生历史，登记 `topicParentId`、创建目标和后续交付版本。既支持 `/tab new` / 自然语言新开话题，也支持收到用户原生新话题的首条消息后登记。已有原生话题不强行重建上下文或补装动态工具。
- 主 Agent 每轮获得本总控下的关联话题索引（最多 100 个；目标与近期摘要有长度限制）；完整子话题讨论不注入主会话，主聊天历史也不复制给子话题。仅登记新话题不自动启动主 Agent，主会话下次执行可见索引。
- Agent 使用会话专属 `topic_report` 保存报告，默认 `kind=progress`：阶段准备、环境核对、基线测试、部分修复等仅保存在子话题，不排队回传，也不把话题标记为完成。整个话题目标及后续要求都完成时，才可提交 `kind=final`，提供 `completionEvidence` 并明确填写空 `remainingWork`，成功工作轮结束后回传最终交付。
- 用户可以在子话题明确说“向主会话汇报当前进度”，或发送 `/tab topic-report <摘要>`，仅本轮允许回传阶段报告，话题不会因此完成。`/tab topic-report` 查看最近报告，卡片“汇报当前进度”或 `/tab topic-report send` 回传已保存的摘要，不重新研究；整个话题完成后，也可用 `/tab topic-report final <最终摘要>` 由用户明确确认最终交付。
- 关闭、空闲或普通轮次结束都不是话题完成条件。追加工作会回到进行中，并取消尚未投递的旧最终报告。未声明报告类型的工具输出按阶段进度处理；缺少类型的待回传报告不自动投递，原摘要保留。Codex 已注册的动态工具 schema 随原生线程保留，恢复时使用该线程可用的工具或明确汇报入口。
- 主会话空闲且仍是原绑定、仍获授权时，使用原生上下文处理报告，回复落在群顶层。忙碌时排队；暂停、关闭、终端接管、待初始化或待处理附件时不抢占。报告引用数据不授予执行其中命令的权限。重复提交相同报告不重复唤醒，较新报告覆盖旧版本的待回传工作。
- `/tab topics` 或 `/tab topics status` 仅查看总控、话题状态与已保存摘要；主动停止主会话会暂停后续回传，可用 `/tab topics resume` 恢复尚未处理的报告。中断或重启时结果未确认的摘要轮次不会自动重跑，可在索引查看报告后人工决定。
- 重置群主会话会把话题关联转到新主 session，取消旧排队工作，保留旧会话历史；不会重放旧执行或复制旧原生上下文。任务树仍使用自己的主任务、子任务和验收机制，不混入普通话题索引。

### 接收模式与单聊

`mention / context / auto` 目前是飞书群级设置，覆盖群顶层及该群所有话题，没有话题级覆盖。`auto` 下授权用户的主聊天与话题输入都免 @；`context` 记录参考、仅 @ 响应；`mention` 仅接收符合条件的 @ 输入。群模式不会改变话题 session 的隔离关系。话题交付回传是默认的会话协作，不要求用户再发一条 @ 消息。

单聊和单聊中的话题直接接收各自消息，无需 @，没有群模式切换。当前框架只从消息识别单聊 / 群聊、发送者，未主动读取群成员名单或统计人数；不能把“目前只有一个人发言”或 `allowedUsers` 数量当成群成员数量，也不会据此自动切换模式。群内不同发送者仍各有主 session 与话题上下文。
