# 交付报告与可复用经验

状态：2026-11-12 实现。报告适用于开发、测试、部署、研究及其他任务，不要求按固定流水线拆分。

交付报告回答“本任务交付了什么、依据和验证是什么、后续如何接续”；可复用经验是报告内提炼的“在什么条件下采用什么做法、有哪些限制”。经验保留来源报告与版本，不替代具体任务的验收或交付。IM 的任务与交付菜单直接解释这两项，不要求用户选择其他项目。交付报告读取当前会话；经验检索可以参考同一 BOT、聊天和用户授权范围内其他会话的报告。

## 何时产生

- 关闭 Session：持久化报告请求，等待当前工作轮取消并保存公开输出后，再冻结记录范围、异步总结。关闭并不表示目标完成；没有已验收成果时报告标为“尚未确认完成”，列出遗留事项。重复关闭不重复建报告。
- 取消任务子树：为各节点保存幂等的“已取消”报告，等待正在取消的工作轮保存已有公开输出；不视为目标完成。
- `task_report` 提交成果：为当前任务成果版本建立报告。子任务先为“已提交，待验收”，直接父任务 `task_review` 接受后为“目标已完成”；拒绝则标记未完成，返工成果使用新版本。
- Dashboard 的“交付与经验 → 生成 / 重新总结”或 `/tab report refresh`：主动整理当前已有记录。生成报告本身不执行任务、重开会话或重新验收。

重开会话后再次关闭会生成下一版本；旧报告截断在重开前，不混入后续工作。服务重启只恢复未完成的总结队列，不恢复中断的工作副作用。历史已关闭会话不会在升级时被批量唤醒或自动总结，可按需手动生成。

## 报告内容与可信边界

每份报告具有独立 ID、Session、可选 Task ID / 成果 revision、会话内递增版本、生成触发来源和状态。正文包含：

| 内容                   | 用途                                                       |
| ---------------------- | ---------------------------------------------------------- |
| 交付概述与产物位置     | 明确实际实现、研究或交付了什么                             |
| 接续规格               | 接口、输入输出、约束、研究口径、方法与假设；资料不足时留空 |
| 验证记录               | 区分执行 Agent 已报告的检查和未验证的主张                  |
| 风险、遗留事项、下一步 | 供父任务验收或下游继续推进                                 |
| 可复用经验             | 适用条件、做法、限制和来源依据，不把猜测当经验             |

总结器读取最近最多 200 条公开记录，总文本预算 48,000 字符；工具只保留名称、状态和退出码，不采集完整工具参数或私有推理。截断会在报告中说明。可引用的经验依据限于已提供的 event ID 和真实存在的 task-result。结构校验不等于事实审计；接续 Agent 仍需核对实际文件、接口与验收标准。

执行 Agent 可在 `task_report` 的可选 `handoff` 中直接提交上述结构化信息；否则使用独立、无工具权限的原生总结轮。Codex 使用新建 ephemeral thread、read-only sandbox、关闭 MCP/工具并限制 JSON 输出；不恢复用户工作 thread。Claude 使用无工具、非持久化结构化查询。实现使用的原生协议见 [App Server 官方说明](https://learn.chatgpt.com/docs/app-server)。

总结服务不可用时仍保留已有成果和最后公开回复，标记为“已记录事实”并展示明确提示；不会推断额外经验或虚构验证通过。可稍后重新总结。报告请求先落库，运行中断后沿用原 ID / 版本恢复。

## 父任务与下游如何接续

报告就绪后，框架把索引和摘要写入直接父会话，以及同一任务树中已声明依赖它的任务。此动作不自动启动普通聊天，也不把全部历史复制给其他 Session。

编排任务的依赖必须先验收通过，并具有匹配成果 revision 的可用报告，下游才调度。调度前将所用报告 ID、版本、任务 revision 固定写入 `TaskJob.inputReports`，可追溯“测试依据的是哪一版编码交付”。首次执行附带依赖报告；多报告正文总预算 36,000 字符，过长时保留版本索引，明确要求使用 `task_report_read` 获取全文。

例如“编码 → 测试 → 上线”：测试声明依赖编码，编码提交产物、接口规格和已执行验证，由父任务验收；测试使用对应版本报告核验。上线再依赖已验收的测试报告。调研工作同样可按“资料收集 → 方法核验 → 结论汇总”使用，不内置领域专用状态机。

原生工具：`task_report_read({reportId})` 读取本任务、下级或已声明依赖的报告；`task_experience({query})` 查找授权范围内的经验。主任务只能验收直接子任务。报告可用、工作轮结束、空闲或关闭都不替代任务验收。

## 展示与存储

- Dashboard：任务详情的“交付与经验”，查看历史版本、生成状态、规格、验证、经验和来源 ID，可加载更早报告。
- IM：`/tab report` 查看最近报告；`/tab report refresh` 主动总结；`/tab experience 关键词` 检索经验。本会话菜单“任务与交付”提供入口。各通道沿用自身支持的卡片或文字展示。
- SQLite：原有 `state.sqlite` 内新增 `session_reports`，正文以 JSON 保存，索引覆盖 Session 版本、Task revision、待处理状态和授权 scope；不另建数据库，不清空历史。
- 经验作为版本化报告的一部分保存，检索结果携带报告 ID / 版本；目前不是向量库，也不自动修改 Agent 的全局系统提示词。

IM 读取与自动回传限制在相同平台、BOT、聊天和用户范围内；任务工具还校验祖先/已声明依赖关系。其他用户或聊天不会因经验检索获得报告。本机 Dashboard bearer token 本来就有全局管理权限，API 继续沿用该边界。

## API 与实现

- `GET /api/sessions/:id/reports?before=<version>`：每页最多 20 份，按版本倒序。
- `POST /api/sessions/:id/reports`：`{ "key": "可选UUID" }`，返回 202；同 Session 同 key 幂等。
- `GET /api/experiences?sessionId=<id>&q=<关键词>`：按会话授权范围检索；本机管理员省略 sessionId 可查全局。
- `/api/state.sessionReportStates`：轻量更新时间索引，正文按需加载。状态查询支持 ETag / If-None-Match，未变化返回 304。

主要实现：`core/report-model.ts`（结构与总结约束）、`core/report-store.ts`（持久化与索引）、`core/session-reports.ts`（队列与范围校验）、`core/tasks.ts`（验收、依赖与固定版本）、`agents/topic-router.ts`（受限原生生成）、`web/server.ts` / `web/public/dashboard.js`（API 和展示）。

`test/session-reports.test.ts` 覆盖关闭与重开、活动轮收尾、幂等与恢复、总结故障降级、访问边界、通用依赖流程、版本引用、分页、ETag，以及异步生成期间验收状态不被覆盖。
