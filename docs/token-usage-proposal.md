# 每会话 Token 用量展示方案（已确认）

目标：每个会话能直接看到累计输入、输出、缓存，以及当前上下文和本轮消耗；飞书与 Dashboard 使用同一份统计结果。本文件记录已确认的设计；实际行为及采集边界见 [管理卡片](management-cards.md#token-用量与压缩对比)。

## 1. 展示内容与统计口径

| 指标            | 定义                                                       | 展示规则                                                             |
| --------------- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| 当前上下文      | 原生最新上报的上下文占用                                   | 有窗口容量时显示数量、容量、百分比；调用参考值明确标注“最近调用参考” |
| 本轮消耗        | 一次框架执行轮次内所有模型调用的用量                       | 运行时显示“本轮已采集”；结束后显示“最近一轮”；自动续跑是新轮次       |
| 会话累计        | 当前会话对应原生会话的累计用量，或框架从采集起点记录的累计 | 明确区分“原生会话累计”和“已采集累计”，并显示完整性                   |
| 最近调用        | 最近一次可识别模型调用的用量                               | 放入详情；不能代替本轮或会话累计                                     |
| 输入            | 本方案统一展示为普通输入、缓存读取、缓存写入之和           | 缓存项是输入的组成部分，不能再加入总消耗                             |
| 缓存读取 / 写入 | 原生实际报告的两类缓存 Token 数                            | 分开展示；不支持或未上报时显示“未上报”                               |
| 输出            | 原生输出，归一化后包含可确认的思考 Token                   | 思考为可选明细，不能重复计入总消耗                                   |
| 合计            | 同口径的输入 + 输出                                        | 原生合计与分项不能可靠对齐时，保留原生值并标明口径，不强行补齐       |

保留原始字段和原始作用域，在展示层计算“输入合计”，避免直接改变现有归一化字段含义。已知缓存读取、写入均未重复包含时，输入合计 = 现有 inputTokens + cacheWriteInputTokens。缺失字段不自行补零；无法确认完整性时标记“部分统计”。

缓存读取占比仅在同一作用域的输入和缓存数据齐全、输入大于零时显示，分母为上述输入合计。名称使用“缓存读取占输入”，不把 Token 比例解释成请求命中率或节省费用。

## 2. 会话展示示例

以下均为示意数据，K/M 为缩写；详情提供精确整数。

```text
Token 用量
当前上下文  64K / 200K · 32.0%（原生估算）
会话累计    1.20M（原生会话累计）
  输入      1.05M       输出       150K
  缓存读取  840K        缓存写入   50K
最近一轮    120K
  输入      100K        输出        20K
  缓存读取   80K        缓存写入     5K
更新于 14:32:08 · 查看明细
```

该示例累计输入中的普通输入为 160K；最近一轮普通输入为 15K。示例中缓存已包含在输入中，所以累计合计是 1.20M。

- 飞书会话信息卡：默认显示上下文、累计及其输入/输出/缓存、本轮合计；独立“Token 明细”折叠区展开上述完整布局、最近调用、采样时间、来源、完整性和最近压缩对比。其他聊天渠道以相同字段提供文本展示。
- Dashboard 会话列表：每行显示累计、输入/输出、上下文占比；缺失时显示状态文字。列表直接使用缓存摘要，不对全部会话同步扫描原生文件。
- Dashboard 会话详情：固定用量区展示当前上下文，并用“最近一轮 / 会话累计”两列对比输入、输出、缓存读取、缓存写入、思考、合计；下方可查看逐轮记录。
- 运行期间“本轮已采集”持续更新；下一轮开始后立即切换当前轮，未获得采样时显示“等待本轮上报”，上一轮数据留在历史中。
- 每个会话默认只展示自身用量；子会话单列，父会话不叠加子会话，避免重复计数。供应商已包含的内部子 Agent 用量只计一次，无法分拆时注明。

## 3. 各 Agent 的采集方案

本节描述当前仓库实现及拟补充能力，不把当前字段当作跨版本协议保证。

| Agent       | 当前实现                                                                       | 本轮与累计的补充方案                                                                                                                                           |
| ----------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Codex       | 已采集最近调用、原生会话累计、上下文、窗口；已有只读历史补查                   | 有可靠轮初基线时，通过累计差值得到本轮；会话累计直接使用最新有效原生累计，重复通知覆盖                                                                         |
| Claude Code | 已采集主 Agent 消息 usage 和成功 result.modelUsage；后者目前按本次原生调用解释 | 以安装 SDK 的说明为准：恢复会话可能延续已保存的 modelUsage；使用原生流水线累计快照覆盖，有可靠基线时计算轮次增量，不能直接跨查询相加；采集失败结果中的可用用量 |
| OpenCode    | 当前只采集最终响应 tokens                                                      | 补充本轮所有 assistant message 的用量采集，以 message ID 去重；覆盖完整后再形成该轮累计；不能把最终消息冒充整轮                                                |

实施时先用安装版本的 SDK、事件结构和协议样本确认“消息、查询、原生累计”的作用域，再确定适配器能力。无法取得完整记录的 Agent 仍展示已确认数据，并标注缺失范围。

Codex 的框架采集累计与原生会话累计是两种视角，不相加。原生累计可能包含用户在原生终端中的执行；本轮仅在边界清楚、没有并发原生写入时计算差值，否则显示无法准确归属。

## 4. 数据与更新方式

扩展现有 usage 事件，补上 sessionId、nativeId、runId、operationId、来源事件/消息 ID、实际模型（有原生上报时）、采样时间、作用域、完整性和原始分项。记录本次原始采样，避免把合并后的旧字段再次当成新事件累计。手动压缩使用独立 operationId。

新增可持久化的轮次汇总和会话摘要：

- 会话摘要：当前上下文快照、原生累计快照、已采集累计、当前/最近轮次、各指标采样时间及来源。
- 轮次汇总：轮次 ID、开始/结束、执行类型、完成/中断/失败状态、输入/输出/缓存明细、累计差值基线和统计完整性。
- 以原生事件或消息标识幂等更新；无唯一标识的累计快照只覆盖，不能每次相加。计数下降或作用域改变时开启新统计段，先重新确认基线，不生成负用量。
- 原始事件、轮次汇总、摘要在同一事务内更新；唯一键防止重启或重放后重复计数。查询读取摘要，不扫描完整事件历史。
- 提供统一的会话用量读取接口，卡片、详情、执行记录、压缩面板复用同一统计服务；现有接口保留兼容字段。
- 网页沿用现有状态更新机制；飞书卡片建议最多每 5 秒合并刷新一次，轮次结束立即刷新。不因刷新统计而调用模型。
- 采样时间按上下文、当前轮和累计分别保存，不能用一次新输出更新掩盖旧上下文的采样时间。

## 5. 历史、压缩和异常规则

1. 历史会话：先使用已保存的有效快照；Codex 可复用现有原生只读补查。无法可靠归属的历史事件不参与本轮累计，也不伪造逐轮明细。
2. 采集中途启用：保留原生累计基线；框架累计注明“自某时起采集”，旧轮次显示“历史未采集”。不宣称已恢复完整历史。
3. 压缩：只可能降低上下文占用；累计不清零。压缩消耗单独归类，可确认后计入会话累计，不能同时按操作和原生累计差值重复计入。压缩后未获得有效占用时显示“待原生更新”。
4. 停止、失败、重启：已确认用量保留，未结算部分标记“部分统计 / 最终值未确认”；失败不等于零消耗。
5. 重置上下文：沿用现有重置行为，新原生作用域重新统计，旧用量保留在历史记录；普通会话新建框架会话，任务会话保留框架 ID。仅关闭、重命名或恢复同一原生会话不清零。
6. 模型切换：有实际模型字段时分别记录并汇总；只有用户配置时不将其标成实际执行模型。窗口等待原生新样本，避免沿用旧模型容量。
7. 零与缺失：明确上报 0 才显示 0；未上报、暂不支持、部分采集、等待更新分别展示。

## 6. 实施顺序与验收

第一步：统一字段口径、补充轮次标识和幂等持久化，验证三个适配器的能力边界。

第二步：上线飞书会话卡片和 Dashboard 列表/详情展示，共享统计服务；旧会话使用已有快照并标明历史覆盖范围。

第三步：补全逐轮查询、异常和历史兼容验证。第一版包含输入、输出、缓存读取/写入、本轮、累计、上下文、采样来源及完整性；费用估算、预算提醒、跨会话总榜不在本次范围。

验收以这些行为为准：

- 每个新旧会话都能找到用量入口；核心分项直接可见，未知项有明确状态。
- 示例中缓存仅作为输入组成，不额外抬高合计；思考仅作为输出组成。
- 重复事件、恢复连接、服务重启不增加同一笔消耗。
- 多次模型调用形成一轮完整用量；只有最近调用时不显示为整轮。
- 手动压缩的上下文前后变化与累计消耗互不混淆。
- 中断、失败、缺失基线、终端接管、原生计数回退均不生成虚假完整数据。
- 父子会话、不同 Agent 和原生 ID 不串数据；两端同一采样的数字及口径一致。
- 大量历史会话列表读取摘要，打开用量页不调用模型、不改变会话活跃时间。

已确认统一输入口径、默认展示层级和自身会话统计范围；实施中按 SDK 的恢复累计语义修正 Claude 采集方式。
